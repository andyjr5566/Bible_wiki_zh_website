# 整站驗收案例與證據要求

以下是 R00–R24 的驗收規格，不是已執行結果。Luna 每次填實際 build／工作樹 hash、日期、環境、命令、觀察、產物路徑。不能沿用舊測試數字當新結果。

## 環境與取證

桌面主要視口1440×900，另測1920×1080；手機390×844與360×800；平板768×1024。記devicePixelRatio、瀏覽器版本、裝置/OS、WebGL renderer（可取時）、品質檔、profile、網路與cache條件。viewport模擬只證明排版／操作，不證明真實手機GPU表現。

每個3D截圖附JSON/文字receipt：asset ID、activeAssetIds、載入URL、衍生hash、模型版本、camera pose/FOV、overlay/drawer狀態、剖面、光照、viewport。來源：正式runtime診斷、網路response紀錄與檔案hash，不靠截圖猜。

比較圖先指定固定光照/鏡位/viewport，再替換before/after資產；若必須改鏡位另交同資產的鏡位比較，不把兩種變化混成材質改善。Blender圖不能代替Three.js驗收。標準截圖至少：完整會幕、剖面、六器物成品、約櫃構造示意、三種角色衣裝、六程序關鍵步、五祭比較、來源drawer、手機全景/半展/閱讀、載入失敗與恢復。

每個QA ID都填 PASS／FAIL／UNVERIFIED、執行人/模型、證據路徑及問題。FAIL修復後儲存前一次記錄，別刪掉失敗歷史。

## 效能門檻（工程目標，不是聲稱已測）

在R00固定可重複裝置與網路設定：正常桌面1440×900、DPR上限2；載入中與穩定互動分開測。

- 同一件器物、同裝置鏡位與功能的衍生修改：三次載入中位數及穩定frame interval中位數相對基準增幅≤10%。基準不可穩定重複時不得用百分比宣稱透過。
- 完整新體驗桌面穩定互動：連續60秒rAF幀間隔p95≤33.3ms；真實手機目標p95≤50ms。模擬viewport只能標桌面窄屏結果。
- 在已記錄20Mbps／50ms RTT測試條件下，冷啟動先可讀UI≤2秒，首個有用3D幀目標≤8秒；detail選擇有立即loading狀態（≤100ms），未快取detail目標≤3秒。工具無法提供準確限速時另記真實網路條件，不混用預算結果。
- 「首個有用3D幀」定義為對應資源ready、相機完成有效取景並至少渲染一幀；下載結束時間不等同這個指標。
- 效能表同時保留P50/P95/樣本數、bytes、渲染呼叫/triangles、幾何/貼圖數和明顯long tasks。不能用FPS瞬間值或bundle大小代替互動效能。
- 沒真實GPU timer時只能報告CPU/幀間隔，不稱GPU耗時。無真實手機則手機GPU未驗證；R24明列限制，不偽造PASS。
- 單次執行的慢幀不能憑主觀刪掉；記錄冷/熱、後臺標籤頁、devtools是否開啟。失敗則先找載入/解析/貼圖/陰影/動畫具體瓶頸，不能刪儀式或角色來縮小目標。

## 學習驗收

R23由不熟悉本專案的讀者按下列問題操作，記錄可否自行找到答案、使用入口、卡點，不編造時間/訪談。無真人參與時由代理走查標為scripted，真實新讀者測試留未驗證給R24。

1. 找到外院、聖所、至聖所，說明能觀看幔內不代表普通人獲准進入。
2. 點約櫃說明成品材質與木芯剖面的區別，並找到出25對應原文。
3. 找到普通祭司、獻祭者、大祭司與利未人的職責依據。
4. 選擇一個燔祭分支，找出誰做哪一步、與另一個分支有何不同。
5. 區分日常香壇供職與贖罪日帶香入幔的情境。
6. 在贖罪日找到麻衣、兩隻羊及退出後的步驟；不能只學到「一年進去一次」。
7. 指出燈臺/盆哪些尺寸未詳載、肘換算為什麼是顯示選擇。
8. 從一個考古比較條目解釋它支援什麼、為何不能證明模型就是出埃及時的原貌。

強制交付是站內能獨立完成以上查詢；真實讀者觀察屬於證據型別之一，缺少時明確限制。任何答案需依靠開發者口頭補充、或站內只有TODO，相關任務不透過。
