## 0. 一句話目標

做一個公開的、高動態的單頁長捲軸網站「耶和華的節期」（站名取自利23:2）。網站順著一年從正月走到七月，再拉遠到安息年與禧年，把摩西五經裡**所有**節日講清楚。視覺參考 Awwwards SOTD 的 Santioni Spirits（Active Theory，2026-10-05）：插畫感的 WebGL、招牌互動、聲音、轉場不斷線。內容層把 raw_data 裡的四套註釋與 STEP 原文證據帶上網站，每一句都對得回來源。

**第一階段只做垂直切片：開場月相＋逾越節整段，然後停下來交給使用者驗收。**

## 2. 不能違反的規則

### 來源
- 經文本文只能從 `raw_scripture/<書卷>/第x章.txt` 取，由建置腳本抽出，不手打、不改寫。和合本女性主詞用「他」。
- 註釋只能從本章 `source_manifest.md` 宣告的 `raw_data/` 檔案取。引用的語料只用**本章**的 raw；同一套註釋的相鄰章容易混引。
- 註釋四家：CT（ccbiblestudy 逐節註解）、GT（ccbiblestudy 拾穗）、KC（KingComments）、BH（BibleHub Study）。GT 裡面還收了別的子來源（例如《舊約背景註釋》），掛名時要寫到子來源，不要誤植成 BH。
- 英文來源（KC、BH）的引用格式：英文原句放在「」裡，中譯緊接放在（）裡；或者具名轉述、不加引號。**中譯不可以放進「」。**
- 引文要短：每家每節期最多一兩句逐字引文，其餘用具名轉述；每段都附原站連結，網址取自 manifest 的 URL 欄。
- STEP 是原文證據層，不是第五套註釋，不算一票。lexicon 列的是可能的義域，不等於這一節的語境義。**STEP 沒列出某個意思，不能當作否定的證據。** 寫法順序：先寫 STEP 能確認的字形、lemma、Strong、詞形、本節譯義，再寫「部分註釋進一步理解為……」。
- STEP 只用 MCP 精確查詢（`query_step_context`、`find_step_occurrences`）取得，不 dump 全文，不查網路上的 STEP。
- 希伯來字母和音譯必須在本章來源中實際出現過。例如利23:24 的「吹角」，原文是不是 shofar 要先查 STEP 才能寫；利25:9 才明確寫到角。
- 經文自己交代的理由（例如利23:43、申16:12、出12:26–27）要標出原句。網站不替經文補充解釋。
- 知識庫內容不搬上網站：名稱＋一句簡介＋「查看完整條目（另開網頁）」，連結照民33 的 `entryUrl()` 寫法。
- 網站缺的資料可以上網查，但要附來源；建置時不連網，產物進版控。
- 聲音只用 CC0，每個檔案在 `data/audio-sources.yaml` 記下：來源頁網址、作者、授權、下載日期。授權要實際打開授權頁確認，不能只看搜尋結果。

### 寫作
- 繁體中文，寫給一般大眾：先講白話結論，段落短，原文編號不寫在句子中間。
- 不寫 AI 腔：不用「不是X而是Y」的對仗轉折、假掉書袋的開場、導覽口吻、空泛昇華的句尾、湊成三點的排比。
- 正文不出現流程或版本註記。
- 粗體節制；`==高亮==` 每段最多一處。

### 網站工程（過去踩過的坑）
- 不自動捲動頁面，不用 `scrollIntoView`；動畫跟著讀者的捲動走，不劫持捲動。
- reduced-motion 分兩種處理：背景裝飾性的動態（`motionOff`）可以停；讀者自己觸發的播放（`animOff` 另外判斷）照常播放，不能變成一格一格跳過去。時間差 `dt` 要夾在 0 以上。這台電腦就開著 reduced-motion。
- CSS class 一律加前綴 `jf-`，避免撞到舊站樣式。
- 建置一律用 PowerShell 跑；用 Bash 跑 vite 會被應用程式控制擋住 rollup 的原生模組。
- 視覺效果要用 headless Chrome 實際截圖確認，不憑想像寫。手機寬度要量 `scrollWidth`，不能有橫向捲動。**只關自己開的 Chrome**，不要 `Stop-Process` 掉所有 chrome。
- Blender 匯出 glTF 時要 `use_active_scene=True`，並先看檔案大小；物件撞名產生的 `.001` 要清掉。新模型要拍全尺寸大圖檢查。
- 長距離走路的動畫：起步和到達用正常速度，中間高速移動，不跳過。
- 要有新手導覽 dialog；回報時把閘門術語翻成白話。
- 不 `git checkout` 還原看不懂的改動；vault 裡常有並行、還沒提交的產物。

## 4. 動線：讓整個網站順順地流下去

這是使用者特別要求的重點。原則如下：

1. **整頁只有一個持續存在的舞台**。WebGL canvas 固定在背景，從頭到尾不卸載、不換頁；捲動只推動同一條時間軸。轉場靠配色漸變、網點密度變化、鏡頭推移完成，不做硬切。
2. **季節當接縫**：夜空（正月）→ 大麥田（初熟）→ 小麥轉金（七七節）→ 秋天的果實和枝葉（七月）。前一段的結尾畫面，就是下一段的開場畫面。
3. **每個節日的內部節奏都一樣**，讀者讀過一段就知道下一段怎麼讀：
   進場畫面 → 日期和經文 → 招牌互動 → 經文自己交代的理由 → 各家註釋怎麼說（就地展開）→ 原文關鍵字（點開才看）→ 延伸連結。
4. **捲動直接帶動畫面**（scrub），不是捲到某處觸發一段固定長度的動畫；讀者停下來，畫面也停。pinned 區段不超過兩三個螢幕高，避免讀者以為網站卡住。
5. **月份導覽**：側邊（手機版在底部）一條細線顯示現在讀到幾月幾日。點了以後**由讀者自己的捲動位置換算跳轉**，跳轉時有短轉場，但不做會連帶捲走整頁的平滑捲動。
6. **高潮放在結尾**：「七的節奏」做成漩渦式拉遠：一天 → 七天 → 七個七天 → 第七個月 → 第七年 → 七個七年 → 禧年吹角。最後回到開場的夜空，首尾相接。
7. 文字永遠留在網頁層（DOM），不畫進 canvas：可以選取、放大、讓螢幕報讀器朗讀，也能被搜尋到。
8. 手機版用拖曳和長按取代滑鼠跟隨。依手機效能自動降低畫質；跑不動 WebGL 的裝置改用預先輸出的靜態插圖，內容一樣都不少。

## 5. 資料層

照律法地圖的架構（Vite 5 + 原生 TypeScript + vitest；建置腳本是 `scripts/build-data.mjs`），放在 `appendix/website/摩西五經/耶和華的節期/`。

- `data/feasts.yaml`：節日、日期、經文出處、條目名稱、配色。**不寫任何解說文字。**
- `data/commentary.yaml`：每節日每家註釋一筆，欄位包括 `source`（CT／GT／KC／BH，GT 要附子來源）、`chapter`、`quote`（逐字引文）、`quote_zh`（英文來源的中譯）、`paraphrase`（具名轉述）、`url`（取自 manifest）。
- `data/step.yaml`：關鍵字的 STEP 查詢結果，包括原文、音譯、Strong、詞形、本節譯義、簡要義域，並記下查詢用的參數，方便重現。
- `data/audio-sources.yaml`：CC0 音檔清單。
- 建置時會擋下以下錯誤，任一條不過就建置失敗：
  1. 經文出處對不到 `raw_scripture`
  2. `quote` 在指定章的 raw 裡找不到逐字原文（先把標點正規化再比對；短於 10 字的引文另外用較低門檻比對）
  3. 條目連結指到不存在的條目
  4. 希伯來字母或音譯在本章來源裡沒出現過
  5. 民28–29 的獻祭數字和經文不一致（從經文重新計算，不手抄）
  6. 音檔沒有授權紀錄
- 底部要有授權頁：和合本、STEP Bible（CC BY 4.0）、四套註釋的原站連結、每個音檔的出處。
- 決定建置方式前，先看 `build.py` 的 `export_vite_apps` 和現有部署位置。單一檔案打包（`vite-plugin-singlefile`）放音檔和材質可能會太大；改成多檔前，先確認部署流程能接受。

## 8. 模型分工

主 session（Opus 5.5）負責所有判斷與創意；Sonnet 和 Haiku 只接**規格寫清楚的工作**，而且交回來的東西一定要由主 session 驗收。

**硬規則：研經內容只能由 Opus 寫。** 挑選要引哪一句註釋、寫具名轉述、把 KC／BH 譯成中文、寫 STEP 字義的說明、寫節日的介紹文字、挑經文自己交代的理由——這些都不能交給 Sonnet 或 Haiku（AGENTS.md：不得靜默改用 Sonnet／Haiku 做內容）。

### Opus（主 session，自己做）
- 讀四套註釋的原文，決定每個節日要用哪些引文和轉述，寫 `commentary.yaml`、`step.yaml` 的內容欄位
- 動線、分鏡、配色、互動手感的設計；每段轉場的規格書
- 所有文字的撰寫與修訂
- 驗收子代理交回的成果：看 diff、看截圖和影片，不能只看「完成」兩個字
- 跟 Codex reviewer 的往返，以及跟使用者的溝通

### Sonnet（照規格寫程式的工程子代理）
- `scripts/build-data.mjs` 與 §5 的六項建置檢查，以及 vitest 測試
- 網點／墨線 shader、Three.js 場景、GSAP ScrollTrigger 時間軸——依 Opus 寫好的分鏡規格實作
- 互動實作：塗門框、搖禾捆、長按吹角、棚子組裝、長條圖動畫
- 手機觸控、效能分級、WebGL 不可用時的靜態插圖退路
- 無障礙：鍵盤操作、ARIA、對比度
- Blender 建模腳本（依 Opus 給的造型規格）
- headless Chrome 截圖與錄影腳本

### Haiku（大量、機械性、有標準答案的檢查）
- 把 `feasts.yaml` 每個經文出處對到 `raw_scripture`，列出對不到的
- 逐條確認 `commentary.yaml` 的 `url` 和 manifest 一致
- 跑建置和測試，把錯誤整理成白話清單
- 量每張截圖的 `scrollWidth`，列出橫向捲動與破版
- 搜集 CC0 音檔候選，列出來源頁網址與授權欄位（最後的授權確認由 Opus 打開頁面親自看）
- 掃描 `jf-` 前綴遺漏、CSS class 撞名、`scrollIntoView` 殘留

### 派工規則
- 派工前先用 `run_pipeline` 取得程式脈絡，把結果放進子代理的 prompt；不讓子代理自己到處搜尋程式碼。
- prompt 要寫清楚：要改哪些檔案、驗收標準、哪些規則不能違反（附上 §2 的相關條目）、要交回什麼（diff 摘要、截圖路徑、測試輸出）。
- 子代理不得修改 `raw_data/`、`raw_scripture/`、`link_folder/`、`.tmp/`、`util/`。
- 同一個檔案不同時派給兩個子代理。互不相干的工作才平行派出去，並設定 `run_in_background`。
- 子代理說「完成」不等於完成：主 session 要親自跑建置、看截圖之後才算數。

## 9. 每次回報的格式

只寫白話的結論數字和需要使用者決定的事項，不貼完整報告，不丟閘門術語。零改動的部分也要明說，例如「12 個節日的經文出處全部對過，沒有錯」。
