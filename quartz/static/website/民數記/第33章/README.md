# 曠野四十二站

民數記 33 章的互動旅程地圖：從蘭塞到摩押平原的四十二站，加上時間比例、民33／民20–22／申10 三處經文的站名對照，以及每一站位置的可信度。2D 為主，不含 3D。技術為 Vite、TypeScript、原生 DOM（SVG 地圖）。非商業研經用途。

## 本機啟動

```powershell
npm ci
npm run dev        # http://127.0.0.1:3043/
npm run build      # 先跑 typecheck 與資料閘門，通過才產生 dist/
npm run preview    # http://127.0.0.1:4195/
```

可部署的是 `dist/`；`appendix/website/build.py` 只在 `dist/index.html` 存在時才把本站列入附錄，`04 民數記/第33章.md` 的「互動網站」連結與 `04 民數記/全書目錄及綱要.md` 的互動網站段，由 `util/build_appendix_links.py` 產生。

## 頁面不會被自動捲動

播放、選站、點地名，都不會移動整個頁面；頁面只在使用者明確要求時才捲：

- **播放**：左欄跟著走動的人時，只捲左欄自己（`scrollTop`），不用 `scrollIntoView`（它會連頁面一起捲，每到一站就把讀者拉回去）；使用者自己在左欄捲動之後 8 秒內也不再跟隨。播放中不會開小卡，也不會移動頁面。
- **點地名／站**（時間軸、分段格子、日期表、清單沒說的事，以及手機上的清單）：資訊卡如果看不到，頁面不動，改在畫面下方開一張**小卡**（`src/ui/peek.ts`）：站名、經文、時間、位置、發生的事（最多兩件）、上一站／下一站。資訊卡看得到（桌機的地圖區）就什麼都不做。
- **到地圖看**：小卡上的按鈕才會把頁面捲到地圖，並在畫面下方留一顆「回到剛才讀的地方」，按一下（或自己捲回原位附近）就回去繼續讀（`src/ui/reveal.ts`）。
- 帶站號的網址（`#s12`、`#play`）一打開就帶到地圖，那是使用者自己要的。
- 手機的資訊卡是固定高度（約 56vh）、內部捲動：換一站時卡片高度不變，下面正在讀的內容不會被推來推去，清單也離卡片近。

每一筆資料都帶證據等級（經文明說／綜合整理／註釋解讀／經文沒說）與經節。`src/data/data.test.ts` 是資料閘門，`npm run build` 前一定會跑：

- **站序由經文推出**：民33:5-48 每一節都要有「從〔前一站〕起行」，站名出現在該節；「起行」共 41 節，也就是 42 站；經節依序（第 1 站在 v3、第 2–34 站是 n+3、第 35–42 站是 n+6）。
- 「」摘句必須逐字出現在所引經節（和合本 `raw_scripture/`，涵蓋創、出、民、申、書）；經節必須存在；「經文明說」一定要有經節和摘句；「經文沒說」不附摘句。
- 註釋家與地圖說明的原話必須逐字出現在 `Voice.file` 指的檔案：本庫民數記 33 章主檔的「」內、地點與解經爭議條目的「」內、`raw_data/` 的 CT 來源檔、FHL〈民圖五〉說明文字；轉述必須帶關鍵詞，關鍵詞也要出現在該檔。
- CT 的〔原文字義〕〔靈意註解〕逐字出現在 CT 來源檔對應的那一行。
- 分段：CT 12＋21＋9、GT 六程各七站，兩種分法都蓋住 1–42；GT 串珠的數字對應（第 5 站供水、第 6 站死亡、兩程之間的類同）用站號算得出來。
- 位置：每站有候選；候選依分數排序；可信度由分數機械推出（高 ≥ 700、中 ≥ 400、低 ≥ 100；「一帶」最高算低、代表點最高算中）；每站都有落在地圖範圍內的位置；同一座標的站會散開；三十八年那一段：中間值落在可信候選的外框裡、淡圈圈住每個可信候選、站與站不疊在一起且不離中間值太遠、推開結果每次一樣。
- 對照表：共同地名兩邊都有；每個站名都出現在所引經節。
- 日期：換算函式的幾個已知值；日期依站序與時間遞增。
- `places.json`、`verses.json` 和來源檔一致（改了條目或經文要重跑對應指令）。

需要對照 vault 裡的 `raw_scripture/`、主檔、條目與 `raw_data/` 的項目，在 vault 外（例如 CI）會自動略過；repo 只帶著已產生的 JSON。

## 位置是怎麼來的

經文只給站名，**沒有座標**。這一點是本站最需要老實交代的事。

- 每一站的候選現代地點與分數取自 [OpenBible.info《Bible Geocoding Data》](https://www.openbible.info/geo/)，授權 CC BY 4.0（<https://github.com/openbibleinfo/Bible-Geocoding-Data>）。本站只取了其中與這四十二站有關的地名，保留候選的名稱、座標、種類與分數，並把座標四捨五入到小數點後四位。分數是 OpenBible 的綜合分數（網友投票加路線時間一致性），只表示各候選之間的相對可信度。
- 預設位置是分數最高的候選；少數例外（以倘、勒撒、哈摩拿）在 `PICK` 寫明理由，畫面與資訊卡都會顯示，被排開的候選也都列出。
- 知識庫的地點條目、信望愛聖經地圖〈民圖五〉（<https://bible.fhl.net/LMAP/index.php?gid=024>）另有一條線的說法（例如 GT 說以倘最有可能是西勒），並列在資訊卡上；只引它們的說明文字，沒有使用它們的圖片。
- 沒有座標的站（第 7 站紅海邊，來源只給了整片水域）依前後站畫在路線上，標「不詳」。
- **三十八年那一段（第 16–31 站）畫在候選的中間值，並用淡圈圈出範圍**：這一段大多數站的位置本來就不明（FHL：「除了以甸迦別和加低斯兩地之外，其它的位置都無法確定」），OpenBible 的候選有的分散、有的多站共用同一個座標。做法（`sites.ts` 的 `zoneOf()`）：
  - **可信候選**：分數 > 0 且不低於該站最高分的 35%（低分的雜訊候選不計入，但仍列在資訊卡）。
  - **位置**：可信候選的分數加權平均（中間值）。有些站只有一個可信候選，就是那個點。
  - **淡圈半徑**：候選離中間值最遠的距離；候選自己若是「某點 N 公里內」，至少取 N；最小 8 公里。
  - **不會擠成一團**：多站落在同一點或靠得太近時，`geo.ts` 的 `relaxZones()` 用固定次數、固定順序的推開演算法把它們輕輕撥開（最小間距 24 地圖單位），結果每次一樣，也保證不疊在一起。
  - **不加文字**：站牌外圈一個淡虛線環表示「位置只是候選的中間值」；淡圈平常不畫，只有選到或走到的那一站才浮現它自己的圈，圈裡再顯示各個候選點；圖例只有一個小圖示「淡圈：可能在這一帶」。這一段站與站之間的連線也畫得更淡（順序與位置都不確定）。
  - 資訊卡的候選表會標「計入」，並說明中間值怎麼來的；各站的候選座標仍完整列出。
- OpenBible 的候選名稱多半是英文短語（「within 50 km of Mithkah」），`candLabel()` 把常見句型換成中文（「離『密加』50 公里內」）；遺址與乾河的名字保留原文。

底圖是 [Natural Earth](https://www.naturalearthdata.com/about/terms-of-use/) 的海岸線、湖與河（公有領域），是現代地形，不是三千多年前的樣子。

- 走動的人與雲柱的樣子（民9:15-23：雲彩收上去，他們就起行）。

## 動態

播放是連續的，不是一站一站跳：

- **播放頭**（`src/ui/playhead.ts`）：走動的人的位置是 1–42 的小數，地圖、時間顯示都訂閱它。「每站一樣久」每段有起步、加速、減速、停一下，時間依兩站的距離；「照時間比例」連續前進、中間不停，四十年約一分鐘。點選站或按上一站、下一站，是沿路線滑過去。
- **地圖**：走動的人走路時手腳擺動；走過的路留下一條有光暈的軌跡；到站有漣漪；頭上的雲柱輕輕浮動（夜間是閃爍的火柱）。鏡頭有緩動（每一格往目標靠近），按鈕、選站、跟隨都是滑過去；拖曳和雙指縮放才即時跟手。跟隨時朝走動的人前面一點，進到三十八年那一片自動拉近。
- **介面**：卡片換內容時淡入，清單、時間軸標記、按鈕都用過渡，不是瞬間換。
- **減少動態**：播放是使用者按了才有的動作，所以就算作業系統設定了「減少動態」（`prefers-reduced-motion`），走動的人還是會移動，只有裝飾性的動畫（雲柱浮動、漣漪、開場光點、路線的流動）會停用。頂列的「減少動態」按鈕（`data-motion="off"`）把播放也關掉：一站一站跳，鏡頭不滑動。程式裡分兩個判斷：`animOff()` 只看頁面自己的開關；`motionOff()` 含作業系統偏好。
- **時間差**：每一格的時間差上限 250 ms，慢的機器只是格數少、速度仍然對；`requestAnimationFrame` 的時間戳可能比記下的起點早一點，所以時間差不可為負（曾經因此讓緩動函數在 [0,1] 之外爆掉）。

### 效能量測（headless、軟體 GPU）

用 CDP Tracing 量過：穩定狀態每格都在 headless 的下限（約 31 ms）；GPU 執行緒的時間幾乎都花在 `SwapBuffers`（軟體模擬 GPU 送出畫面），主執行緒 3.5 秒只用約 0.9 秒。SVG 文字在縮放時會重新排版（`FindSvgTextChunks`），所以縮放動畫比平移貴；有真的 GPU 的機器會順很多。
