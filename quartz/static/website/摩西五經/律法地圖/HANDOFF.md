## 一、這個專案是什麼

**一句話**：一個查摩西五經（創世記到申命記）律法的互動網站。使用者可以從生活問題、主題、書卷或經文找到一條律法，看到和合本經文、一句話說明、別卷（出埃及記、利未記、申命記）又記了一次的對照，以及連回知識庫的出處。

**給誰看**：從剛認識聖經的人到研究聖經的人，用同一個畫面。深淺靠內容順序與就地展開，**沒有**「入門／查經／研究」之類的模式切換（使用者明說過那樣太誇張）。

**設計初衷**（使用者給的）：律法的原文 תּוֹרָה（妥拉）字義是指引、教導，律法是神給人的引導，不是冷冰冰的規條。所以網站不替經文解釋精神，改讓**經文自己交代理由**：很多律法旁邊跟著一句原因（例如利25:42「因為他們是我的僕人，是我從埃及地領出來的」），網站把這一節的和合本原句標出來。首頁標語是詩篇1:2。

**它不是什麼**：不是註釋書，也不是知識庫的副本。網站自己只有三樣東西：和合本經文、每條一句重述經文的話、律法之間的結構（分類、段落、關聯）。人物、地方、觀念、解經的內容都在知識庫，網站只放名稱加一句簡介，再放「查看完整條目（另開網頁）」。

**位置**：`appendix/website/摩西五經/律法地圖/`（在 Hermes scripture 這個 vault 裡）。

**技術**：Vite 5 + 原生 TypeScript（沒有框架）+ vitest。`npm run build` 產生單一檔案 `dist/index.html`（約 800 KB，JS、CSS、資料全部內嵌），從 Obsidian 以 `file://` 打開就能用。

## 二、開工前先做這幾件事

1. 讀 `README.md`（資料格式、指令、程式結構、規則）。這份 `HANDOFF.md` 管「還有什麼要做」，README 管「這個東西怎麼運作」。
2. 在 **PowerShell** 跑（Bash 跑 vite 會被應用程式控制擋住）：
   ```
   cd "C:\Obsidian\Hermes\scripture\appendix\website\摩西五經\律法地圖"
   npm run data     # 讀 data/*.yaml 和 vault，產生 src/data/explorer.json，並跑所有資料檢查
   npm run build    # 資料是否最新 → tsc → 51 個測試 → vite 打包
   ```
   兩個都要是綠的才算健康。改了 `data/` 底下任何檔案，一定要重跑 `npm run data`，否則 build 會說「資料過期」。
3. 想看畫面：dev 伺服器 `npm run dev`（使用者常開在 http://127.0.0.1:3051/），或用 headless Chrome 截圖（作法在 README「驗證」，**只能關你自己開的 Chrome**，不要 `Get-Process chrome | Stop-Process`，那會關掉使用者正在用的瀏覽器）。

## 四、資料怎麼放（一頁版）

所有手寫的東西都在 `data/`；`src/data/explorer.json` 是自動產生的，不要手改。

- `data/laws/*.yaml`：條文（最重要）。一個檔案可以收好幾章；同一卷可以分好幾個檔，檔名 `書名-xx-yy.yaml`，裡面的 `book:` 一樣。**同一章不要拆在兩個檔案裡**（覆蓋率會算錯）。
  - 每章有 `excluded`（不收的節與理由）和 `sections`（段落，底下是 `laws`）。
  - 每條有：`id`（例 `lev25-39`）、`title`（≤30 字）、`refs`（經節範圍）、`topics`（子題 id）、`summary`（一句話，≤90 字）、`basis`（說明依據哪幾節）、`why`（選填，經文自己交代理由的節號，只標節號）、`entries`（選填，對應的知識庫條目名稱）。
- `data/topics.yaml`：6 大類、47 個子題。
- `data/relations.yaml`：關聯。`from`、`to`、`type`（`parallel` 平行重述／`supplement` 補充修訂／`case` 案例／`cites` 引用）、`evidence`（知識庫條目名稱＋逐字引句，或某章「本章整理」＋逐字引句）。
- `data/questions.yaml`：首頁問題卡。`data/tours.yaml`：照順序讀的路線。`data/glossary.yaml`：術語對應條目。
- 經文取自 `raw_scripture/<書名>/第N章.txt`（第 N 行＝第 N 節），經文裡的人物地方觀念取自各章 `.tmp/第N章/verse_links.yaml`，條目類型取自 `util/output/link_index.json`。這些都是自動讀的。

建置時 `scripts/build-data.mjs` 會擋下錯誤，常遇到的：
- 一句話超過 90 字、標題超過 30 字。
- 用了「她」（和合本女性主詞用「他」）、用了「不是…而是」「讓我們」之類的公式句、出現 Strong 編號或來源代號（CT/GT/KC/BH/STEP）。
- 一句話和依據經文的用字重疊太低（可能加了經文沒說的東西）。
- 關聯的引句沒有逐字出現在知識庫條目裡，或引句裡的經文參照沒有同時涵蓋兩端的條文。

## 五、不能違反的規則

1. **只重述經文，不加解釋。** 一句話只能說經文說了什麼，不能寫「象徵」「預表」「意味著」「提醒我們」這類字眼。找不到經文依據的話一律不寫。
2. **不搬知識庫的內容。** 條目只放名稱＋一句簡介＋「查看完整條目（另開網頁）」。
3. **關聯一定要有出處。** 沒有知識庫裡逐字的句子可引，就不連線。寧可少，不要編。
4. **嚴禁 AI 公式文。** 介面文字、問句、路線名稱、導覽都平實交代內容。禁「不是…而是」「是…，不是…」「不只是…更…」、「讓我們／探索／帶你／旅程」、「X：Y」口號式標題、空泛昇華的結尾、湊三個一組的排比。有一個測試會掃 `src/**/*.ts` 裡所有中文字串，命中就建置失敗。這是使用者特別強調過的。
5. **點擊不捲動頁面。** 不用 `scrollIntoView`。要看的東西用原地展開（`<details>`、peek 小卡）。換頁時才回到頂端。
6. **全部用繁體中文。** 對使用者回報時，把內部檢查翻成白話（例：不要貼「白話說明超過 90 字」，要說「一句話限 90 字，我縮短了」）。使用者不懂程式術語。
7. **不確定的事用問題問使用者**（`AskUserQuestion`），尤其是：分類怎麼分、要不要寫進網站畫面、要不要動知識庫。
8. **commit 只在使用者同意的範圍內做**，只 `git add` 這個資料夾。這個 repo 有人在背景自動 commit（訊息是檔案清單），你自己的 commit 要寫清楚訊息。
9. **不要動知識庫的檔案**（`link_folder/`、各書卷章節 md）。那是另一套嚴格流程（見根目錄 `AGENTS.md`），這個專案的任務裡只有明確標示「寫知識庫」的幾項會碰到，而且要先問使用者。

## 八、踩過的坑
